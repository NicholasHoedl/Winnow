# ADR-0007: A Hand-Written Service Worker, Not @serwist/next

**Status:** Accepted (T6b-S3)
**Date:** 2026-07-28

## Context

T6b adds the app's first service worker. Two earlier documents pre-committed the tooling,
and both are superseded by this one:

- `ARCHITECTURE.md` §6.2 said the worker "will be generated by a standard Workbox-based
  Next.js PWA plugin rather than hand-rolled", while explicitly flagging that the choice
  should be re-verified at implementation time because "this is a fast-moving corner of the
  ecosystem".
- `docs/IMPROVEMENT-PLAN.md` named **`@serwist/next`** as the dependency.

The scope actually being built is narrower than either anticipated: **static assets plus an
offline fallback page, and no user data cached at all.** No page, RSC payload, or API
response is ever written to disk.

That scope is not timidity. §6.2's rule that dynamic pages stay network-only is load-bearing
in ways that are easy to miss — `ensureRecurringTasks()` materialises and retires rows
*during a page read* (page rendering is the scheduler; there is no cron), every hub freezes
"today" into its HTML at render time, `revalidatePath()` cannot reach Cache Storage, and
`signOutAction` cannot clear it. Caching navigations would quietly break all four.

ADR-0006 also set the standing bar: **a new runtime dependency needs an argument, not a
preference.**

## Decision

**Hand-write `public/sw.js`.** No build step, no plugin, no new dependency.

The whole file is a version constant, a five-entry precache list, and a six-branch fetch
handler. Cache-first for `/_next/static/*` and the precached files; network-only for
everything else; the offline page served only when a **navigation** rejects at the network
layer.

The single fact that makes this viable without any build integration: **everything Next
emits under `/_next/static/` is content-hashed.** Immutable URLs mean cache-first per URL
can never serve something stale, so the precache manifest — the main thing a plugin
generates — buys nothing here.

## Consequences

- **Zero new dependencies**, against ~80 lines of code that has to be maintained by hand.

- **No precache manifest, so no cold-start caching.** A runtime cache is empty until the
  first online visit. Only the five stable-named files (`offline.html`, the committed font,
  three icons) are available before then. Acceptable: the offline page is exactly what a
  cold start needs, and it is one of the five.

- **The RSC/document distinction had to be got right by hand, and it is the sharpest edge
  in the file.** App Router client navigation fetches the *same path* with `?_rsc=<hash>`,
  expecting a Flight payload; answering it with `offline.html` breaks the router in a way
  that is very hard to trace back. The handler keys on `request.mode === "navigate"`, never
  on the URL. This is precisely the discrimination a library would own, and it is covered by
  a test that fails if the condition is rewritten in terms of the path.

- **A 307 or a 500 is passed through untouched.** Only a network *rejection* triggers the
  fallback. Getting this backwards would make an expired session look like an outage, with
  no way to sign back in — also covered by a test that fails on `!response.ok`.

- **Every precached path must be exempt from the proxy matcher in `src/proxy.ts`.** This bit
  during implementation: `/fonts/*.woff2` was not exempt, so it answered 307 to `/login`;
  `cache.addAll` is all-or-nothing and `cache.put` rejects a redirected Response, so one
  missing exemption meant no offline support at all, silently. `src/components/pwa/sw.test.ts`
  now drives the real install handler and asserts every path it requests is un-gated.

- **The worker only registers in production builds**, because dev chunk filenames are not
  content-hashed and cache-first would serve stale code and break HMR. Consequence: the
  ordinary `pnpm test:e2e` cannot exercise it, so there is a second Playwright config
  (`playwright.prod.config.ts`, `pnpm test:e2e:prod`) that pays for a real build. In dev the
  component actively *unregisters* any worker it finds, so a local production build cannot
  leave one behind to poison the dev server.

- **No `skipWaiting()`.** A first install activates immediately (there is nothing to wait
  for) and calls `clients.claim()`; an update waits for open tabs to close. That keeps the
  old worker serving a tab whose chunk hashes the new build no longer has.

- **A worker outlives a bad deploy.** If the fetch handler ever ships broken, users keep it
  until it is replaced. That is the reason the file is kept short enough to read in one
  sitting and why `activate` deletes by version prefix.

## Alternatives considered

**`@serwist/next` in config mode.** The strongest alternative, and genuinely viable — the
"it needs webpack" objection is dead. `@serwist/turbopack` 9.3.0 (2025-12-20) backported
Turbopack support to the stable 9 line, and `@serwist/next` 9.4.0 (2025-12-26) added a
config mode that touches no bundler at all; the whole line is actively maintained (9.5.12,
2026-07-22). Rejected on value, not viability: its central feature, `precachePrerendered`,
has nothing to precache here, because every route in this app is dynamic and auth-gated. It
also changes `build` to `next build && serwist build` and pulls in `esbuild`.

**`@serwist/turbopack` (route-handler mode).** Rejected on a concrete open bug:
[serwist#360](https://github.com/serwist/serwist/issues/360) (opened 2026-07-21, still open)
— `createSerwistRoute` hides its `next/dist/server/config.js` import from `@vercel/nft`
static analysis, so the module is never traced into the output bundle and the route throws
`ERR_MODULE_NOT_FOUND` at request time. `output: "standalone"`, which this app uses, relies
on that same tracing. The maintainer's own workaround is to use config mode with
`precachePrerendered: false` — i.e. the option we would have adopted it for.

**`next-pwa`.** Dead. Last published 2022-08-23; its own issue tracker points users
elsewhere. Webpack-only.

**`@ducanh2912/next-pwa`.** Last published 2024-09-18 and its `peerDependencies` still
require `webpack >=5.9.0`. Written by the same author as Serwist, who now points users at
Serwist.

## When to revisit

**If the scope ever grows to caching navigations.** At that point RSC/document
discrimination, precache revisioning, and deterministic eviction stop being three branches
and start being a library's job — and Serwist is the right one. That change would also mean
reopening `ARCHITECTURE.md` §6.2 on its merits rather than, as here, cashing in the half of
it that already permitted static-shell caching.
